## A. autonomy 側

### A-1. 【観測中】IMU のデータ化け — 検出はするが、いまは弾いていない

> 化けではなく **断** (`imu_timeout`) は A-18。

`/state/imu` に物理的にありえないサンプルが混入する。実機 (BNO055) で確認したもの:

* **ノルムが 0 のクォータニオン** — 静止 60 秒で 2 件 (約 30 秒に 1 回)
* **角速度が 3 軸とも ±35.6 rad/s** — int16 フルスケール (32767/16 = 2047.9 deg/s) と一致
* **0.5 秒で −3° → −170° → −4° の姿勢跳躍** — 運動中に出やすい

`navigator_node` / `auto_target_generator` / `rl_attitude_node` はいずれも角速度を
ヨーレートとして、姿勢をそのまま制御・観測に使うため、**1 発のスパイクで制御が跳ねる**。

**実装済み**: `umiusi_common/imu_sanity.py` の `ImuSanity`。3 ノードすべての IMU
コールバックに入れてある。

> **2026-08-21 の方針変更 — 既定では捨てない (`imu_sanity_enforce: false`)。**
> 実機で測ったところ、判定に引っかかるのは **0.44%** しかなく（下記）、一方で
> **フィルタ自身が誤爆したときの被害のほうが大きい**ことが分かった（姿勢基準が飛んだあと
> 144 秒間ずっと棄却し続けた）。閾値を決めるにはまずデータが要るので、いまは
> **検出とログだけ行い、値はそのまま通す**。`imu_sanity_enforce:=true` で従来どおり捨てる。
>
> 唯一の例外は **ノルムが 0 のクォータニオン**。これは閾値の問題ではなく正規化そのものが
> 定義できない（0 除算）ので、`enforce` に関係なく直前の有効値を返す。
>
> ログは「破棄した」のか「検出したが通した」のかを言い分ける（`ImuSanity.describe`）。
> **データを集めてから閾値と運用を決め直すこと。**

| パラメータ | 既定 | 意味 |
|---|---:|---|
| `imu_sanity_enforce` | **false** | true にすると検出したサンプルを破棄する。既定は検出のみ |
| `imu_max_gyro` | 10.0 rad/s | 検出の閾値 (フルスケールは 35.74) |
| `imu_max_step_deg` | 30.0 deg | 1 サンプルの姿勢跳躍上限。50 Hz なら 1500 deg/s 相当 |

ROS 非依存の純関数なので単体テストできる。**実機で観測した実際の化け値を使ったテスト**が
`umiusi_rl_control/test/test_imu_sanity.py` にある。
符号反転 (q と −q) を急変と誤判定しないこと、正常な運動 (1 サンプル 30° まで) を
通すことも確認済み。

#### 実機で検証した結果 (2026-08-21、機体を手で 150 秒振った bag)

**閾値は妥当だった。棄却しているのは「速い運動」ではなく明確な読み出し化けだった。**

- 実際に動かしたときの角速度は最大 **4.6 rad/s** (閾値 10 に対し 2.2 倍の余裕)、
  1 サンプルの姿勢変化は最大 **6.1 deg** (閾値 30 に対し 4.9 倍の余裕)。
- **BNO055 の姿勢と角速度はよく整合している**。棄却されなかった 7453 サンプルで、
  実際の姿勢変化と「角速度 × dt」の差は **中央値 0.004° / p99 1.25°**。ノイジーではない。
- 棄却されたのは 150 秒で 33 件 (0.44%):
  - **ノルム異常 24 件** — `|q|` が 0.000122 / 1.106 / 2.1307 / **2.230613 (10 回、同じ値)**。
    正常なクォータニオンは常に `|q|`=1 で、運動しても変わらない。しかも**機体が静止して
    いる (gyro 0.00) ときにも出る**。同じ値が繰り返すのはビット単位の読み出し化けを示唆する。
  - **角速度スパイク 9 件** — 1906〜2034 deg/s。前後のサンプルは 0.2〜3.8 rad/s で、
    **孤立した 1 サンプルだけが飛んでいる** (20 ms で 0.28 → 35.51 → 0.28 rad/s は
    角加速度 1775 rad/s² に相当し、物理的にありえない)。姿勢は同時刻に動いていない。

#### そのうえで見つかった不具合 — 姿勢が飛ぶと復帰できなかった

t=6.04s に **姿勢基準そのものが 169° 飛び、飛んだ先で正常に追従を続ける**事象が出た
(`|q|`=1.000、以降なめらか、角速度からの予測はわずか 2.1°)。跳躍は「最後に *採用* した
値」との差分で見るため、比較対象が飛ぶ前の姿勢に固定され、**残り 144 秒をすべて棄却し
続けた** (棄却率 96%、連続棄却 7202 回)。姿勢が古い値に貼り付くので、制御は事実上盲目になる。

**修正** (`enforce=true` にしたときのために残してある): `stale` (連続棄却が `stale_after`
超) に達したら**跳躍チェックだけを解除して再同期する**。絶対値で判定できるノルム異常とフルスケール化けは弾き続ける。同じ bag で
再生すると棄却率 **96.0% → 0.52%**、連続棄却 **7202 → 6 回** (120 ms で復帰)。
`rl_attitude_node` は再同期時に警告を出す — **目標姿勢は飛ぶ前の基準で与えられているので、
飛んだあとは目標を入れ直す必要がある**。

> 残る問題は **IMU 側**。150 秒に 1 回とはいえ姿勢基準が飛ぶので、水中で起きると
> その瞬間に目標姿勢の意味が変わる。BNO055 のキャリブレーション状態
> (`CALIB_STAT` レジスタ) を確認・記録することを検討する。

#### 跳躍の軸を分解した (2026-09-29) — **飛んだのはヨーだけ。磁気基準の問題**

同じ bag (`data/imu/20260821-080906-imu-motion`) で、連続する 2 サンプルの**相対回転**を取り、
その回転軸を world (重力基準) 系に直して見た。オイラー角の変化率を body 角速度と比べる
やり方は結合で汚れるが、**相対回転の軸**なら汚れない。

```
t=6.040s dt=20.1ms |ang|=169.09deg
  droll=+1.64  dpitch=-0.55  dyaw=-169.03
  axis_world=(-0.013, -0.008, -1.000)     |q|=1.00000   gyro=(+1.74,-0.58,-0.03)
```

- **回転軸は ほぼ完全に重力軸まわり** — つまり **roll/pitch は動かず、ヨーだけが約 180° 飛んだ**
- `|q|` = 1.00000 なので**読み出し化けではない**。融合が**別の磁気方位に収束し直した**形
- 同時刻の **gyro_z = −0.03 rad/s** — 実際には回っていない
- 7504 サンプル中、20 ms スケールで 30° を超える跳躍は**この 1 件だけ**

→ **重力基準 (roll/pitch) と磁気基準 (yaw) で信頼度がはっきり違う。** 壊れ方も「ドリフト」
ではなく **約 180° の跳躍**で、hard-iron 由来の解の取り違えの典型。BLDC 4 基が IMU の直下に
ある構成と整合する。

#### ベンチで測り直した結果 (2026-09-06、control スタック、機体は静止)

bag は `mujoco_ws/data/imu_long_20260906/{imu_long,imu_cam}`。

**「長時間 run で周期が劣化する」は否定された。** 915 秒回して **50.001 Hz / 100 ms 超の
欠落 0 件 / 間隔 max 20.99 ms**、前半後半とも mean 20.000 ms で時間依存の劣化は無い。
カメラを有効にした 775 秒の run でも **50.001 Hz / 欠落 0 件** (間隔 max だけ 23.57 ms に増える)。
2026-08-25 の 935 秒 run で見えた 48.5 Hz・最大欠落 15.4 s は **run の長さが原因ではなく
負荷依存**。今回との差分は「水中 / armed (CAN 送信あり) / autonomy スタック / モータ稼働」で、
**モータの EMI が次の候補**。

**化け率は電気的負荷でスケールする**:

| 条件 | 化け率 | 出た型 |
|---|---:|---|
| 静穏ベンチ (915 s) | 0.0153% | `\|q\|` = 1.2e-4 |
| カメラ ON (775 s) | 0.0361% | 上に加えて `\|q\|` = 2.227 |
| 2026-08-25 水中 run | 0.13% | (上の 8/21 の記録と同系) |

**化けはすべて単発でバーストしない** (静穏 915 秒の 7 件は連続長 [1,1,1,1,1,1,1])。
つまり**棄却は 1 サンプルの前値保持で足り、複数サンプルのホールド機構は要らない**。

**閾値の余裕を実測した (84502 サンプル)**:

- ノルム: 正常サンプルの最悪が `||q|-1| = 0.00795`。**BNO055 の出力は厳密な単位ノルムではない。**
  既定の `quat_tol = 0.01` では余裕が 1.27 倍しか無く、棄却に回すと正常サンプルを弾きかねない。
  いちばん軽い化け (上記 `|q|=1.106`) は 0.106 離れているので、両側から離すなら 0.03 前後。
- 角速度: 正常の最悪は 0.41 rad/s (静止時)。上限 10.0 に対して 24 倍以上の余裕。

**`sinsei_UMIUSI_control` 側の移植では棄却の可否を絶対判定と相対判定で分けた**
(`util/imu_sanity.hpp`)。絶対判定 (NaN/Inf・正規化不能・ノルム・角速度) は履歴に依存せず
ロックアウトしないので既定で棄却し、相対判定 (姿勢の急変) だけを既定で通す。
上記の 144 秒棄却は相対判定でのみ起こる事象なので、絶対判定まで通す必要が無い。
**autonomy 側は単一の `imu_sanity_enforce` のままなので、両スタックで棄却の挙動が違う。**
run を突き合わせるときは注意すること。

### A-11. 【解決済み】指令のレート制限が実機側に無く、sim2real ギャップになっていた

**sim はポリシーの指令をそのまま物理に入れていない。** `configs/umiusi.yaml` の

```yaml
servo_slew_deg_per_s: 250.0   # サーボのレート制限
thrust_slew_per_s: 4.0        # ESC のレート制限
```

で平滑化してから使い、**平滑化後の値を観測にも返している** (`simulator.py` の
`thr.slew(...)`)。つまりポリシーは **レート制限を含むプラント**を制御対象として学習しており、
制限がローパスとしてポリシーの高周波成分を吸収していた。

実機側にこれが無かったため、ポリシーが出す「毎ステップ符号が反転する飽和指令」が
そのままサーボへ行き、追従できずに震えるだけになっていた。

#### 実測 (2026-08-21、bag とオフライン再生)

理想的な観測 (水平・静止・サーボ中立) から閉ループで回したときの**実際のサーボ角度**:

| レート制限 | 実サーボ角 | std | 符号反転 |
|---|---|---:|---:|
| **250 deg/s (sim と同じ)** | 0〜30 deg | 9.9 | **0.0 回/秒** |
| **なし (旧実装)** | ±90 deg | 89.9 | **49.7 回/秒** |
| 500 deg/s | -8〜33 deg | 13.2 | 0.0 回/秒 |
| 100 deg/s | -5〜28 deg | 11.9 | 0.0 回/秒 |

学習時の `servo_n` の std は **0.192 = 実角度 ±17 deg 相当**で、制限ありのほうと一致する。
**制限値には鈍感** (100〜500 deg/s のどれでも振動は消える) なので、実機のサーボの実レートに
厳密に合わせる必要はない。

> **「制限ありで学習したものを制限なしで動かす」ほうが、逆より深刻。** 制限は安全装置では
> なく**プラントの一部**で、ポリシーはそれを前提に「あえて飽和指令を出す」方策
> (バンバン制御に近い) を学習している。制限を外すとその高周波成分がそのまま出て発振する。
> 逆 (制限なしで学習 → 制限ありで実行) なら、ポリシーは元々滑らかな指令を出すので影響は小さい。

**暫定の修正**: `umiusi_rl_control/thruster_limits.py` の `slew` (sim と同じ実装) を
`rl_attitude_node._command()` に入れた。パラメータ `servo_slew_deg_per_s` (既定 250) /
`thrust_slew_per_s` (既定 4.0)、0 以下で無効。**実機では未検証**。

> **レンチモード方策 (`action_mode: modes`) でも外さないこと** (2026-08-29 に一度外して差し戻した)。
> `mode_action.py` の「折返し後を平滑化するな」は**モード座標のスルーの代わりに**出力側へ置くな、
> という意味で、このレート制限とは別物。sim の閉ループ実測 (av_mode13、cap 0.25、DR/外乱オフ、
> 8 エピソード、同一 seed) が差を出している:
>
> | プラント条件 | 零空間シェア |
> |---|---:|
> | **学習時どおり (esc 4.0/s + servo 250 deg/s)** | **4.67%** |
> | ESC ランプ除去 (ノードで外した場合の相当) | 7.66% |
> | ESC ランプ除去 + サーボ 350 deg/s | 7.04% |
>
> **ESC ランプを外すだけで 4.67% → 7.66% (+64%) に増え、受け入れ基準 ≤5% を割る。**
> 方策も seed も同一なので、差はプラントのレート制限だけによる。**ESC 側は実機に等価物が無い**
> — control の `max_duty_step_per_sec` は `/cmd/direct` では素通りする (B-12) ので、
> ノードが掛けなければ誰も掛けない。
>
> ノード側で実際に効いていることは、同一のステップ応答 (`v_cmd` 0 → 0.4) をリミッタ有無で
> 比較して確認済み: **有効時は duty 4.24/s・サーボ 265 deg/s で上限に張り付き**、無効時は
> 25.46/s・9054 deg/s。**計測はティック単位に間引くこと** — 4 トピックがそれぞれ届くので、
> 生のまま差分を取ると dt がマイクロ秒になり 451/s のような嘘の値が出る。

#### ただし本質は「実機の観測が指令のエコー」の疑い

> **恒久対策済み (2026-08-22)**: 新ポリシー (17/14 次元, `proprio_mode: action`) は
> **サーボ角・推力を観測に入れない** — エコーだろうと実測だろうと正帰還に入りようがない。
> `rl_attitude_node` も `/state/thruster_state_all` の購読をやめた (bag には録り続ける)。
> 下記のエコーか実測かの確認 (ステップ応答) は control / LispBM 側の課題として残る。

**リミットは物理的にサーボ側にある。** sim の config も実サーボの実力
(`= ~300..350 deg/s`) を derate した値としている。**なら実機のサーボも物理的に制限され、
±90° の往復は観測できないはず**。ところが bag では **12.5 Hz で ±90° 往復 = 2250 deg/s 相当**
が観測された。物理的にありえない。

→ `/state/thruster_state_all` の `angle` は **実測値ではなく指令のエコー**の疑いが濃い
(RC サーボは位置フィードバックを返さないので、LispBM が指令をそのまま返している可能性)。

| | sim | 実機 |
|---|---|---|
| 指令 | 飽和・高周波 | 飽和・高周波 |
| サーボの実挙動 | slew で制限 | 物理的に制限される (同じ) |
| **観測に返る値** | **制限後の実角度** | **指令のエコー (嘘)** |

つまり **sim は正しく、実機の観測が間違っている**。方策は「指令どおり動いた」という嘘を
見て、さらに極端な指令を出す正帰還に入っていた。上の `slew` は「指令を滑らかにすれば
エコーでも実際と一致する」という副作用で効いているだけで、本質的な修正ではない。

**次回の実機作業で確認すること** (上の恒久対策済み注記のとおり、**これは control / LispBM 側の
課題**。autonomy は `state.angle` を観測に使っていないので、autonomy 側の残作業ではない):

1. **`state.angle` がエコーか実測か** — 指令をステップ状に変えて `state.angle` の応答を見る。
   瞬時に追従すればエコー
2. エコーなら **control / LispBM 側でサーボモデル (レート制限) を通した推定値を返す** ← 本筋
3. autonomy 側の `slew` は指令を実現可能な形に整えるためのもので、2 とは独立に残る

> なお **方策自体は姿勢誤差に応じた制御をしている**。レート制限ありで `ori_err_x` を
> -0.6〜+0.6 で振ると、サーボ角が単調に応答する (lf: 74.0 → 27.7 → -10.6 deg)。
> 制限なしだと ±90° の往復で平均が 0 になり、**制御情報が平均化で消える**。
> レート制限は制御を代行しているのではなく、出力を実現可能な形に戻している。

#### ただし、この(旧)方策はサーボの使い方として成立していない

> **新ポリシーで対策済み**: `av_cal1_best` 系は指令変化ペナルティ (`w_cmd_gap`) と
> サーボ収束モデル入りで再学習しており、sim 評価ではサーボ実駆動は穏やか。実機で
> 下記の計測 (最大速度駆動時間・往復距離) を再確認する。

レート制限が正しく効いている条件 (sim と同じ) で測っても:

| 測定項目 | 結果 |
|---|---|
| **サーボが最大速度で駆動されている時間** | **100.0%** |
| **指令に到達している時間** (差 < 1°) | **0.1%** |
| 指令と実角度の乖離 | 平均 41.3° / 最大 85° |
| 10 秒間の往復距離 / 正味の変位 | **2495° / 10.0°** |

**一度も指令に到達せず、常時全開で動き、99.6% が無駄な往復。** 位置決めサーボは目標角度を
与えて収束させる設計なので、収束前に指令を変え続けると内部制御が常に飽和する。
**常時最大電流 = 発熱と摩耗が最大**で、実機でモータが発熱したのと整合する
(ESC の HFI と併せて二重)。

行動空間は「サーボ角度 (位置)」なのに、学習の結果 **slew を積分器とする速度指令**として
使われており、設計と実態が食い違っている。**sim 側で「指令変化へのペナルティを常時掛けて
到達可能な指令を出させる」のが本筋** (`Umiusi_sim#2`)。制御帯域は落ちるが、249 deg/s で
往復して正味 10° しか動いていない現状に対して失うものはほとんどない。

> なお **rpm 欠損 (B-8) も `vel_cmd=0` (A-9) も、この振動の主因ではなかった**。
> オフライン再生で rpm を健全化しても飽和率は 68.8% → 61.2% しか下がらず、
> `vel_cmd` を 0.4 に戻しても 68.2% のままだった。

### A-17. 【中】`max_duty` を 0.4 に上げるとロール逸脱がほぼ倍になる

やや悪化する見込み)。次の再学習の後にまとめて測り直す:

| `max_duty` | p95 ロール逸脱 (外乱あり) | (外乱なし) | 転覆 (>90°) |
|---:|---:|---:|---:|
| **0.25** | **51°** | 33° | 0% |
| 0.4 | 70° | 60° | 0% |

転覆はどちらも 0% だが、逸脱は倍近い。**当面 0.25 のまま**にし、上げるなら段階的に、

### A-13. 【解決済み】IMU (BNO055) の frame は REP-103 で確定

実機で 1 軸ずつ動かして確認した (2026-08-25、#18 の実験 2)。**3 軸とも REP-103**
(x 前 / y 左 / z 上、右手系) と一致した:

| 軸 | REP-103 での正回転 | 実機の観測 |
|---|---|---|
| **pitch** (y まわり) | 機首が下がる | 首を下げると **+** |
| **yaw** (z まわり) | 左旋回 (上から見て反時計回り) | 上から見て時計回りが **-** |
| **roll** (x まわり) | 左舷が上がる (**機体前方から見て**反時計回り) | 正面から見て時計回りが **-** |

> roll の「正面から見て」は**機体の前方から機体を見る**視点。パイロット視点だと左右が
> 反転して逆の表現になるので、記述するときは視点を明示すること。

**配備契約が REP-103 なので、`Umiusi_sim` の `tools/convert_policy_frame.py` による変換は
不要**。`rep103` 付きのポリシー (`att_cal1_best` / `av_cal1_best` / `av_sim2real2_rep103`)
をそのまま使える。

**残っているのは面内回転** (機体の前方と IMU の x 軸のヨー方向のずれ)。今回の試験で決まったのは
軸の対応と符号だけ。ずれがあるなら別途測る。

### A-12. 【高】スラスタ ID と物理位置の対応が sim と食い違っている疑い

`Umiusi_sim` の `configs/umiusi.yaml` は `id -> name: 1=lf 2=lb 3=rb 4=rf (ASSUMED, verify)`
と自ら未検証を明記しているが、**pivot 座標と命名が矛盾している**:

| id | pivot x | pivot z | 幾何的な位置 | config の命名 |
|---|---:|---:|---|---|
| 1 | -0.023 | -0.187 | **前** | lf |
| 2 | -0.397 | -0.187 | **後** | lb |
| 3 | -0.023 | +0.187 | **前** | **rb** ← 後ろのはず |
| 4 | -0.397 | +0.187 | **後** | **rf** ← 前のはず |

sim は `act_ids = [servo_1..4]` の順で action を割り当て、観測も同じ順。autonomy 側は
`POSITIONS = ("lf", "lb", "rb", "rf")` の順に `action[0..3]` を送るので、**右舷 2 基の前後が
入れ替わる**。ヨーとロールの符号が狂うため、**これが合っていないと他を直しても制御は成立しない**。

CAD frame は「+X 前 / +Y 上」の右手系なので **+Z は左**のはずで、その場合 `1=lf` (左前) も
z<0 = 右になり左右も合わない。

**実機で確認する手順** (水に入れなくてよい。推力方向の確認と同じ要領):

```bash
# 1 基ずつ回して、物理的にどれが動くか目視する
ros2 topic pub --once /cmd/direct/thruster_controller/output_lf \
  sinsei_umiusi_msgs/msg/ThrusterOutput \
  "{runnable: {esc: true, servo: false}, duty_cycle: 0.15, angle: 0.0}"
```

`lf` → `lb` → `rb` → `rf` の順に試し、**前左・後左・後右・前右**の順で回るかを見る。
あわせて `angle` を ±45° にして、サーボの回転方向 (+90 が上か下か) も確認する。

対応が違っていれば **sim 側の `units` の順序を実機に合わせる** (`Umiusi_sim#3`)。

### A-10. 【解決済み】`record_run.sh` を対話シェルで叩くと bag が起動直後に殺される

Keyboard handling disabled.` がログに出ていれば正しく起動している。

### A-7. 【中】e-stop は `ros2 topic pub` の既定 QoS では届かない

`~/estop` の購読側は **TRANSIENT_LOCAL**（再起動時に e-stop 状態を継承するため latch する）。
一方 `ros2 topic pub` の既定は **VOLATILE** で、**Durability が合わずマッチしない**。
`Waiting for at least 1 matching subscription(s)...` が出続けて、**緊急停止が届かない**。
購読側は `ros2 topic info -v` で確認できる（Subscription count は 1 なのに繋がらない）。

```bash
ros2 topic pub --once --qos-durability transient_local \
    /rl_attitude_node/estop std_msgs/msg/Bool "{data: true}"
```

**回すときは手打ちに頼らず `teleop_keyboard` を開いておくこと**（`ESTOP_QOS` を使うので
QoS が確実に合う）:

```bash
ros2 run umiusi_rl_control teleop_keyboard
```

> 実機で踏んだ (2026-08-21)。ドキュメント側が QoS 指定なしのコマンドを載せていたのが原因で、
> 修正済み。**緊急停止の経路は、使う前に必ず「実際に止まるか」を確認すること。**

### A-14. 【高】カメラの内部パラメータが未較正 — 方位角が構造的に狂う

**カメラで位置を固定するなら、ここが最初の前提条件**。「画素 → 方位」が正しくないと、
その上に載せる位置推定も位置固定も全部ずれる。いまはここが未較正なうえ、
**アスペクト比の食い違いで `fx = fy` の前提が壊れている**。

いまの内部モデル (`umiusi_perception/balloon_detector.py` の `_pinhole`):

```python
fy = (height / 2) / tan(fovy / 2);   fx = fy;   cx, cy = width / 2, height / 2
```

- `fovy_deg` の **60 は sim の MuJoCo モデル** (`umiusi.xml` の `front_cam fovy="60"`) の値で、
  実レンズでは未検証。しかも `autonomy.yaml` の 3 ノード (`perception_node` / `navigator_node` /
  `auto_target_generator`) に同じ値が散在していて、直すとき 1 箇所忘れる形になっている。
- **歪み係数も主点較正も無い** (`camera_matrix` / `distortion_coefficients` はどのリポジトリにも無い)。
- `range_m` は **バルーン直径 0.20 m 決め打ち** (`BALLOON_DIAMETER_M`) が唯一のスケール基準。
  **バルーン以外の距離は出せない** ので、位置固定の基準にはそのままでは使えない。

**さらに構造的な問題**: 前方カメラ (cam1) は `1280x720` (16:9) で流しているのに
(`cameras_deploy.yaml` の `pi_camera`)、`camera_bridge_node` は caps で `320x240` (4:3) に
強制する。横 1/4・縦 1/3 と縮尺が違うので、**正方画素の前提が成り立たない**:

| | コードの仮定 | 実際 (潰れる場合) |
|---|---:|---:|
| `fy` (仰角に効く) | 207.8 px | 207.8 px … **一致する** |
| `fx` (方位角に効く) | 207.8 px | **155.9 px** (0.75 倍) |
| 画面端の方位角 | 37.6° | **45.8°** |

つまり **方位角を系統的に過小評価する** (端で 8° ほど内寄りに出る)。`range_m` も
bbox の w/h 平均を使うので、横だけ潰れたぶん偏る。仰角だけは無事。

> **`fx / fy = 0.75` という比は、実レンズの画角が何度であっても変わらない** —
> 16:9 を 4:3 に非等方に潰したことだけから出るため。表の絶対値 (207.8 px / 45.8°) のほうは
> 「実レンズの縦画角も 60°」を仮定した値なので、**較正するまで数字自体は信用しないこと**。

> GStreamer がレターボックスを入れる (`videoscale add-borders`) 場合は壊れ方が変わり、
> 上下に黒帯が入って `cy = height/2` と実効 `fovy` の**両方**がずれる。
> **どちらなのかは 1 フレーム見れば分かる**ので、まずそれを確定させること:
>
> ```bash
> ./tools/record_run.sh --vision --name calib      # 圧縮画像を bag に残す (A-16)
> # 取り出して 1 枚出し、黒帯の有無を見る
> ```

**修正方針** (位置固定を作り始める前にここまでやる):

1. 潰しかレターボックスかを確定し、`camera_bridge_node` の caps を**アスペクト比を保つ**形に
   直す (16:9 のまま 426x240 等) か、`fovy_deg` と別に `fovx_deg` を持たせる。
2. チェッカーボードで内部パラメータを実測し、**`CameraInfo` として publish する** (A-16)。
   **必ず水中で取ること** — 平面ポートの屈折で見かけの画角は空中と変わる。空中の値は使えない。
3. 較正値を 1 箇所に置き、3 ノードに散った `fovy_deg` はそこから引く。
4. カメラ → 機体の外部パラメータ (取り付け位置・向き) も要る。`umiusi_perception/behavior.py` の
   `pin_offset` に「機体上の任意点から見た方位に直す」前例があるが、**手入力で未較正**。

### A-15. 【中】姿勢のみ (14 次元) のポリシーは速度指令を黙って捨てる

`att_cal1_best_rep103` のような **attitude タスク (14 次元) のポリシーは観測に速度指令を
持たない**。それ自体は仕様どおりだが、**捨てていることが操作者からは分からない**:

- `~/setpoint` を受けると `目標を更新: … 速度=[0.40,0.00,0.00] m/s` と**受理したように
  ログが出る**。`~/current_setpoint` にもその速度が載る。
- なのに `_build_obs()` は 14 次元では `v_cmd` を連結しないので、**観測には一切入らない**。
- 読み込み時に `attitude タスクのポリシーです` を **INFO で 1 行**出すだけ。起動から時間が
  経ってから teleop を触ると、まず気付けない。

**ドライ再現で確認済み (2026-08-26、`main` @ `ba7049a` + フェイク IMU)**:

| ポリシー | v_cmd | サージモード `m` (1 秒ビン) |
|---|---:|---:|
| `av_cal1_best_rep103` (17 次元) | 0.0 | ±0.05 未満 (ゼロ近傍) |
| `av_cal1_best_rep103` (17 次元) | 0.4 | **+0.07〜+0.13 が 30 s 持続** (単一符号) |
| `att_cal1_best_rep103` (14 次元) | 0.4 | **−0.02** (出ない) |

`m = (h_lf + h_lb − h_rb − h_rf) / 4`、`h_i = duty_i · cos(angle_i)`。
**17 次元の経路は teleop → setpoint → 観測 → サージまで健全**で、sim の予測 (+0.153) とも整合した。
つまり「前進しない」の原因はノードのコード経路ではなく、**どのポリシーを載せたか**か、
**指令が届いていなかったか**のどちらか (A-9 の 8/25 run はこれを bag から確定できなかった)。

**修正方針**:

1. 14 次元ポリシー稼働中に速度指令を受けたら **WARN を出す** (`_on_setpoint`)。
   `#20`/`#21`/`#22` が `rl_attitude_node.py` を触っているので、**マージ後の別 PR** で入れる。
2. `teleop_keyboard` 側にも、subscriber が 0 のときの警告を入れる (押しても誰も聞いていない)。
3. **記録側は対処済み** — `/rosout` を bag に入れ、`bag_check.py` が
   「14 次元ポリシーなのに速度指令が入っている」を FAIL として出す (A-16)。

### A-16. 【中】カメラで位置を固定するためのデータが run に残らない

映像は RTSP から H264 で直録し、bag には 1 枚も入らない (これ自体は正しい判断 —
`docs/logging.md` の実測で `-a` は容量 200 倍・CPU +30pt)。ただし**視覚で位置を推定する
素材としては、これだけでは足りない**:

- **映像のフレームと bag のイベントを対応づける手段が `meta.txt` の開始壁時計しかない。**
  `rtspsrc` のジッタバッファ (100 ms) と再接続 (`_rN` ファイル) があるので、開始時刻からの
  単純な積算では合わない。「この画のとき機体は何をしていたか」が ms 精度で引けない。
- **`CameraInfo` を誰も publish しない** ので、後から内部パラメータを復元できない (A-14)。
- 位置固定は**姿勢制御の外側のループ**になる (視覚 → 位置誤差 → `v_cmd`)。
  `depth_supervisor.py` が水圧で同じ形をすでにやっているので、**設計はそれを踏襲するのが早い**
  (状態機械 + `v_cmd` の上書き、ポリシーには手を入れない)。

**対処 (このコミット)**: `record_run.sh --vision` で
`/front_cam/image_raw/compressed` と `/front_cam/camera_info` を bag に入れる。
スタックは `record_vision:=true` で起動する (`core_autonomy.launch.py` / `autonomy.launch.py`)。
圧縮画像は **2 Hz に間引く** (`compressed_max_rate_hz`) — JPEG エンコードは perception と
同じ CPU を食うため。全フレームは RTSP 直録が持っているので、bag 側は
**映像と bag を突き合わせる基準**と「そのとき何が見えていたか」があれば足りる。

**残っていること**: `CameraInfo` の publisher 本体 (較正値が無いので A-14 とセット)、
カメラ → 機体の外部パラメータ、位置固定の外側ループそのもの。

### B-4. 【仕様】有線接続はインターネット共有 + mDNS が正規手順

公式 Wiki (raspi-setup-2) の「ネットワーク設定」がこの構成の根拠:

> `/etc/netplan/99-umiusi.yaml` … **PC からのインターネット共有の有無に関わらず、mDNS が
> 動くようにしたいという意図。**
> ```yaml
> eth0: { dhcp4: true, link-local: [ipv4], optional: true }
> ```

つまり:

* **接続は IP ではなく `ssh pi@<機体名>.local` (mDNS)** で行う。固定 IP は使わない
  — **が、実運用で mDNS が引けないことが多く、保険として固定 IP を併記した (B-10)。**
  公式の設定は削っていないので、この項目の内容は引き続き有効
* **PC からのインターネット共有が正規のワークフロー** (Pi が apt / pip / git を使えるようにする)。
  Linux の PC なら `sudo nmcli con mod "<有線接続名>" ipv4.method shared`
* 共有が無くても `link-local: [ipv4]` により `169.254.x.x` を自己割り当てするので mDNS は効く。
  ただし**インターネットは使えない**
* **共有をオンオフした直後は、Pi が経路変更に適応するまで数分かかる** (Wiki に明記あり)

**ファイアウォールに注意。** Wiki も「接続できない場合はファイアウォールをオフにして試す」と
書いている。Linux の PC で `ufw` が有効だと **ROS 2 の DDS が通らず、トピックが一切見えない**:

```bash
sudo ufw allow in on <有線IF> from 10.42.0.0/24
```

SSH だけなら PC 側の ufw は関係ない (PC からの outbound のため)。**PC でも ROS 2 を動かして
Pi と通信する場合にのみ必要。**

### B-10. 【運用】mDNS で入れないことが多い — 固定 IP を保険として併記した

**公式方針 (B-4) は「固定 IP は使わず mDNS で入る」だが、実運用で引けない事例が続いた**ため、
netplan に固定 IP を**併記**した。**公式の設定 (`dhcp4` / `link-local` / `optional`) は
一切削っていない**ので、mDNS も DHCP も従来どおり効く。あくまで詰まったときの保険。

> **この変更は公式 Wiki の方針からの逸脱**。共同開発者と Wiki 側にも共有すること。

Pi 側 `/etc/netplan/99-*.yaml` (`addresses` の行を追加しただけ):

```yaml
network:
  version: 2
  ethernets:
    eth0:
      dhcp4: true                      # 公式のまま
      link-local: [ipv4]               # 公式のまま
      optional: true                   # 公式のまま
      addresses: [192.168.137.2/24]    # ← 追加。Windows ICS のセグメントに合わせた
```

`sudo netplan apply` で反映する。**リモートから適用すると SSH が切れる**ので、
`sudo netplan try` (120 秒で自動ロールバック) のほうが安全。

#### 引けなくなる典型パターン

| 症状 | 原因 |
|---|---|
| HUB / ケーブルを替えた直後から引けない | **Windows がネットワークを作り直し、プロファイルが「パブリック」に戻る**。パブリックだと mDNS がブロックされる |
| `Set-NetConnectionProfile` が失敗する | **管理者 PowerShell で実行していない** (エラー文の 1 番目の理由) |
| 共有を切り替えた直後だけ引けない | Pi が経路変更に適応するまで数分かかる (B-4) |
| そもそも別名で探していた | 機体ごとにホスト名が違う (`umiusi2` / `alexandrite` …) |

Windows 側の復旧 (**管理者 PowerShell**):

```powershell
Get-NetConnectionProfile                                          # 有線が Public なら原因はこれ
Set-NetConnectionProfile -InterfaceIndex <有線の Index> -NetworkCategory Private
Enable-NetFirewallRule -DisplayGroup "mDNS"
```

#### 共有のセグメントは OS で違う

| PC 側 | Pi が取るアドレス |
|---|---|
| **Windows のインターネット共有 (ICS)** | `192.168.137.x` (PC は `192.168.137.1` 固定) |
| **Linux の `nmcli ... ipv4.method shared`** | `10.42.0.x` |
| 共有なし (両者 DHCP なし) | `169.254.x.x` (リンクローカル) |

**固定 IP を振るならどちらのセグメントに合わせるかを決める必要がある。** いまは Windows ICS に
合わせて `192.168.137.2/24` を採用している。Linux から繋ぐ場合は、PC 側を同セグメントに
手動設定するか、従来どおり DHCP / mDNS で繋ぐ。

#### 相手が見つからないときの探し方

```powershell
arp -a | Select-String "192.168.137"     # ICS 環境。Pi の MAC は DC:A6:32 で始まる (Raspberry Pi)
netsh interface ipv6 show neighbors      # fe80:: は MAC 由来なので HUB 交換でも変わらない
ping -6 ff02::1%<有線の Index>           # リンク上の全ノードに問い合わせ
```

### B-12. 【高】`/cmd/direct` は `is_forward` / `max_duty` / スルーレート制限を素通りする

> **上流に修正あり (push 済み・未マージ)**: `sinsei_UMIUSI_control` の
> `fix/actuator-limits-on-direct-cmd` (`8ae6ee7`)。issue #19-5。
> アクチュエータの歯止めを `ThrusterLimits` に切り出し、**指令の出所によらず必ず通す**ように
> した (duty 上限 / `servo_sign` / サーボ角 ±90 クランプ)。
>
> **スルーレート制限は `ThrusterLimits` に置かない** (2026-09-01 に push されて確定)。
> ヘッダが理由を明記している — ステートレスな範囲強制だけを置く方針で、状態を持つ制限を
> 素通し経路に挟むと (a) 生指令をラッチしないと二重に掛かる (b) 実効レートが publisher の
> レートに依存する (c) 較正ツールが生指令を出せない。**持ち主は指令を出す側**
> (autonomy の `thruster_limits.py`)。したがって **autonomy 側の `slew` は撤去しない** —
> これが `/cmd/direct` 経路で唯一のレート制限になる。
>
> (以前ここには、スルーレートを `ThrusterLimits` に含める版 `742407d` を前提にした記述が
> あった。その版は force-push で置き換えられ remote には残っていない。)
>
> **`controllers.yaml` の `max_duty_step_per_sec` を 1.0 -> 4.0 にする変更 (`f00b96e`) は
> このブランチから外れ、`tune/thruster-slew-4-0` に退避している** (2026-09-06 に確認:
> `fix/actuator-limits-on-direct-cmd` の `controllers.yaml` は 1.0 のまま)。
> sim が ESC ランプの domain randomization `[1.0, 10.0]` を入れたので、control の 1.0 は
> **範囲の中**であり揃える必要が無くなった。sim の sweep 実測でも 1.0/s は範囲内で最良
> (ori 0.154 / null_pw 5.2% / 巡航 104%)。以下は退避前の記述。この値は `logic::thruster::LinearAcceleration` に渡り、
> `/cmd/direct` に publisher が居ない経路 — つまり `command_mode: "target"` — の
> スルーレートを決める。sim の `thrust_slew_per_s` (4.0) と長く揃っておらず、
> `"target"` を使うと A-11 と同型のギャップが出る状態だった。既定の `"direct"` では
> `LinearAcceleration` ごとスキップされるので影響しない。
>
> **なお RL 経路 (`/cmd/direct`) はこの値を使わない。** `rl_attitude_node` 自身の
> `thrust_slew_per_s` パラメータ (既定 4.0、`ros2 param set` で実行中に変更可) が効く。
> sim の 4.0 が鏡写しにしているのは control ではなくこちら。
>
> **「方策が 4.0 に張り付いている」は regime 依存。** A-11 の 4.24/s は `v_cmd` 0→0.4 の
> **ステップ過渡**の値。sim の sweep (av_mode13、12 エピソード/点) ではエピソード全体の
> 平均が 1.33/s (上限の 33%)、上限に張り付くのは 25% の step。過渡では律速、定常では余裕あり。
>
> **恒久対策は ESC 側の DR** (2026-09-01 に sim へ `thrust_slew_range: [1.0, 10.0]` を導入)。
> これで control 側の値が何であれ方策が有効になる。範囲の根拠は**リスクの非対称性** —
> 姿勢誤差は 1.0〜無制限でほぼ不変 (0.146-0.165) だが、零空間と巡航は速い側で単調に悪化
> (null 6.1% → 9.1%、巡航 83% → 60%)。未実測の物理 ESC ランプは実効値を遅くする方向にしか
> 働かないので良性側。無制限を範囲に入れないのは「悪いプラントに耐える」方向へ最適化して
> しまうため。下限を実測に置き換えるには、VESC が CAN で返している実 duty / 電流を control が
> state に出す必要がある (いま `vesc_model.cpp` でデコードしたまま捨てている)。
>
> `is_forward` と `duty_per_thrust` は「推力[N] → duty の換算」なので Logic 側に残っている
> — 直接指令はすでに duty で届くため、掛け直すと二重換算になる (A-12 で符号補正不要と確定)。
> **マージされて実機へ入るまで、下記の実態は変わらない。** 入ったら autonomy 側の暫定シム
> (`servo_sign` / `max_duty` / 度変換 / ±90 クランプ) を撤去する。
>
> **撤去を急ぐ必要があるのは `servo_sign` だけ。** 両側が掛けると符号が二度反転して
> 補正が打ち消される (既定 `[1,1,1,1]` / `1.0` のままなら実害は無い)。残りは重ねても
> 壊れない: レート制限は同じ値を直列にしても 1 段目の出力がすでに条件を満たすので
> **べき等**、`max_duty` は厳しい側 (autonomy の 0.25) が効くだけ、±90 クランプも
> べき等、度変換は control 側が持っていないので二重にならない。

`thruster_controller.cpp` の `update()`:

```cpp
const auto has_no_thruster_publishers = ...;
if (has_no_thruster_publishers) {
    this->output = this->logic->update(...);   // ← logic はここでしか呼ばれない
}
this->output.cmd.esc_duty_cycle.value = this->output.state.esc_duty_cycle.value;
```

`/cmd/direct/...` に publisher が居ると **logic ごとスキップ**される。直接指令経路 (較正実験の
`tools/thruster_cmd.py`、`rl_attitude_node`、`navigator_node`) では以下が **一切効かない**:

| パラメータ | 本来の役割 | 直接指令経路での実態 |
|---|---|---|
| `is_forward` | 基ごとの推力向き反転 | control 側では**無視**される。ただし **autonomy が起動時に読みに行って自分で当てる** ようにした (下記 B-14)。設定の正は control の yaml のまま |

直接指令の上書き自体は意図どおりだが、**制御スタック側の歯止めがゼロ**になる点は認識が要る。
max_duty 0.4 プロトコルは `thruster_cmd.py` の自主チェックだけで担保されている。

**帰結**: `is_forward` は control のループでは直接指令に効かない。そこで autonomy 側が
**起動時に `thruster_controller_<pos>/is_forward` をパラメータサービスで読み、`thrust_sign` として

control が居ない構成 (sim bridge / ベンチ) では autonomy 自身の `thrust_sign` に落ち、警告が出る。
サーボ向きは従来どおり `servo_sign` (publish 直前)。

> **A-12 の「ESC 側の向き補正は不要」は 2026-09-12 に否定された。** B-14 を参照。

**上流の修正が入っても、autonomy 側の `thruster_limits.slew` は撤去しない** — 設計 B なら
唯一のレート制限、設計 A でもべき等な重ね掛けにしかならない (上表)。外すと設計 B のとき
A-11 と同型の sim2real ギャップになる。

撤去の優先順位は冒頭の引用ブロックのとおり (`servo_sign` だけが急ぎ)。

### B-13. 【解決済み】`ThrusterOutput.angle` の単位コメントが実装と逆

### B-14. 【原因特定・修正済み】推力の符号が反転している — 姿勢制御が正帰還になる

> **2026-09-13 に原因を特定し、バンドルを修正した。**
>
> **バンドルの `thrust_axes` の符号規約が control と逆だった。** control の
> `feed_forward.hpp` は「z 軸まわりに**反時計回り**を horizontal の正の方向とする」と
> 明記しており（θz 列が 4 基とも +1）、実機の実測（`thrust_sign_check`、servo 0°）でも
> lb/rb/rf の 3 基とも**反時計回り**だった。**機体と control が一致し、バンドルだけが
> 時計回りを正としていた。**
>
> | | 全基の水平出力を正にしたときの回転 |
> |---|---|
> | control の FF | 反時計回り |
> | 実機の実測 | 反時計回り |
> | **バンドル（修正前）** | **時計回り** ← これだけ逆 |
>
> **修正**: `umiusi_autonomy/config/classical_bundle.json` の `thrust_axes` の符号を反転。
> **ハードは触らない** — 触ると control の FF 経路と UI テレオペが逆になる。
>
> **再現と検証**: 実機の規約で力を出す偽機体（6 自由度）に対し、初期 yaw 40° から:
> **旧バンドル → yaw 誤差 160.9°（180° の罠を再現）/ 新バンドル → 0.0°**。
> 深度ドリフトも −2.04 m → −0.14 m。
>
> **⚠ sim の `configs/umiusi.yaml` は旧規約のまま。** `tools/export_classical.py` で
> バンドルを再生成すると**この修正が巻き戻る**。sim 側の扱いは未決（学習済み方策が
> 同じ規約を前提にしているため、単純に反転させると方策が無効になる）。
>
> **`thrust_sign` ではなく `thrust_axes` を直したのは意図的。** `thrust_sign` は duty に
> 掛かるので推力ベクトル全体（水平も垂直も）が反転する。今回確認できたのは**水平の
> 反転だけ**で、垂直は `_Y_UP` で別管理なので `thrust_axes` の反転が正しい。


2026-09-12 のプール実験で、**指令したモーメントと実測の角加速度が 3 軸とも逆相関**していた
(roll −0.27〜−0.46 / pitch −0.41〜−0.57 / **yaw −0.77〜−0.87**、3 区間すべて)。

符号が反転した比例制御では誤差 0 が不安定になり、**誤差 180° が安定平衡**になる。実際
yaw 誤差の中央値は 172°、区間の 64〜95% を 170° 超で過ごし、残った振れが動画で見えた
**0.48〜0.53 Hz のリミットサイクル**（duty は ±0.25 のバンバン）だった。

**モデルに依存しない裏付け**: arm すると全軸が悪化する。

| | disarm | arm |
|---|---:|---:|
| roll std | 2.32° | **3.76°** |
| pitch std | 0.84° | **1.94°** |
| gyro_x std | 1.87 °/s | **5.47 °/s** |
| \|yaw 誤差\| 中央 | 111° | **174°** |

制御が浮力の復元を打ち消している。ある区間では disarm 中 44° だったものが arm 後 172° へ離れた。

**ソフトは自己整合している。** bag の IMU を実際の制御パイプラインに通し直すと、記録された
指令と完全一致する (duty 相関 1.000 / 平均絶対差 0.000)。制御則も配分も誤差を減らす向きに
出している。**IMU も犯人ではない** (gyro と姿勢微分が同符号、傾き +0.76〜+1.09)。
**回転行列は行列式 +1 なので、IMU の取り付け角では 3 軸すべてを反転させられない** — 反転は
必ず駆動側にある。

仮説検定では **推力ベクトル全体の反転**だけが 3 軸すべてを説明した (部分的な鏡像・サーボ
反転・前後左右の入れ替えはどれも 1 軸を外す)。**どの基かは 2026-09-12 の bag からは分離
できない** — 姿勢制御が 4 基を一斉に動かすため duty の相互相関が 1.000 になる。

**切り分け**: まず `tools/thrust_sign_check.py --ground` — **地上で**噴流の向きを目視して
符号を決める（水に入れず、機体を押さえる必要もない。4 基は合力 0 の純粋な偶力配置なので、
噴流の向きが取り付け位置から一意に決まる）。出力がそのまま `is_forward` になる。
**ただし地上で決まるのは符号だけで、バンドルの幾何が正しいかは決まらない** — 幾何が鏡像なら
符号を合わせても水中でまた逆になる。そこで水に浮かべて
`tools/thrust_sign_check.py` が 1 基ずつ励起して基ごとに判定する
(サーボ 0°/60° を分けるので、推力ベクトルごとの反転とサーボの正方向を切り分けられる。
配線の入れ替わり検出も出る)。**4 基すべて測ること。**

**直しかた**: control の `params/controllers.yaml` の `is_forward`。autonomy は起動時に
読みに行く (B-12 の帰結)。現場では `ros2 param set /classical_attitude thrust_sign
'[1.0,-1.0,1.0,-1.0]'` で走らせたまま試せる。

> **ハードを直す前にモデル非依存の確認をすること** (`thruster_cmd.py steady --duty 0.2` で
> 前進が前進か)。バンドルの幾何が誤りならハードを直すと sim で学習した RL 方策まで
> 巻き添えになる。

**関連**: この反転があると、誤検出が無くてもシナリオは「ぐるぐる回る」— FSM が風船の方位へ
向けと指令しても機体は逆に回り、見失って探索に戻る。**認識の調整より符号が先。**

### B-15. 【解決済み】`thruster_cmd.py steady` の「前進」「旋回」が入れ替わっていた

2026-09-13 にバンドルの幾何で計算し直して発見。4 基は接線方向に付いた**偶力配置**なので:

| 符号 | 実際の挙動 |
|---|---|
| 全基同符号 | **合力ちょうど 0 の純粋な旋回**（上から見て右回り） |
| `lf+ lb+ rb- rf-` | **合力が前方のみ（yaw ほぼ 0）の前進** |

`steady` は既定（全基同符号）を「前進」、`--yaw`（`lf+ lb+ rb- rf-`）を「旋回」と
表示していた — **完全に逆**。「前進を指令したのに機体が回る」ので、推力の符号を
確かめようとして逆の結論に至る。方向確認にこのツールを使う場面で直接効く。

ラベルを入れ替えて修正済み。併せて `pose` サブコマンドを追加し、**指令の前に
バンドルの幾何から「何が起きるはずか」を表示する**ようにした（同じ取り違えを
人が再発させないため）。

### B-16. 【高】スラスタ 1 基が死んだときの縮退 — 経路が 2 つあり、片方ずつしか直らない

2026-09-13、**lf の BLDC が故障**。1 基欠損でも動かせるが、**直す場所が 2 つある**。

| 経路 | 誰が配分するか | 縮退の入れかた |
|---|---|---|
| control の `ff` (core の BT / auto_target) | `logic/attitude/feed_forward.hpp` | control の `disabled_thruster: "lf"`（ブランチ `codex/left-front-thruster-failure`） |
| **`/cmd/direct`**（classical / RL / navigator。シナリオと teleop はこちら） | autonomy の `GeneralAllocator` | **autonomy の `live_thrusters`** |

**`/cmd/direct` に publisher が居ると control の logic はスキップされる**ので、
control 側の `disabled_thruster` はシナリオ経路には**効かない**。逆に autonomy だけ直しても
core の BT 経路には効かない。**両方要る。**

ただし同じブランチの **`esc_disabled: true` は direct 経路にも効く**
(`thruster_controller.cpp` の direct 購読が `resolve_thruster_mode(esc_disabled, ...)` を通す)。
つまり control 側だけ入れると:

  lf の ESC は control 層で止まる → **しかし autonomy のアロケータは lf が生きている前提で
  解き続ける** → 解いた wrench と実際に出る力が食い違い、残り 3 基が誤った前提で釣り合いを取る

これは `GeneralAllocator` の docstring が warning している状態そのもの。

> **2026-09-13 時点、control の `codex/left-front-thruster-failure` は main に未マージ。**
> main の `esc_disabled` は 4 基とも false なので、**autonomy は「全基生きている」と読む。**
> マージするか、autonomy 側で `live_thrusters_source:=param` +
> `live_thrusters:='[false,true,true,true]'` を明示すること。

**対処**: autonomy は起動時に control の `esc_disabled` を読みに行き、`live_thrusters` を
自動で合わせる（`live_thrusters_source` 既定 `"control"`。`is_forward` と同じ方式で、
**設定の正は control の yaml 1 箇所**）。control が居なければ自ノードの値に落ちて警告。

**根拠 (1) 静的**: `GeneralAllocator.set_live()` で 1 基を外して解き直すと、縮約した行列の
**rank は 6 のまま、条件数は 5.34 → 8.05**（lf 欠損、2026-09-13 実測）。6 自由度の権限は残る。

**根拠 (2) 指令した wrench がどれだけ実現するか** (lf 死亡、cap 0.4、実測):

| 指令 | live を伝えない | live を伝える |
|---|---:|---:|
| 浮力トリム（下向き 1.17 N） | 22.5% 誤差 | **6.9%** |
| 前進 3 N | 57.2% | **0.2%** |
| yaw トルク 0.5 N·m | **240.2%** | **0.0%** |
| roll トルク 0.3 N·m | 138.8% | **0.0%** |
| 前進 2 N + yaw 0.3 | 70.7% | **0.0%** |

**yaw は 240% 誤差** — 指令しないより悪く、向きまで違う。これが docstring の言う
「死んだ基に指令を出し続け、実現する wrench が黙って違う」状態。

**根拠 (3) 動的** (6 自由度の偽機体で lf を推力ゼロにし、姿勢制御を 40 秒。最後の 8 秒の中央値):

| | live を伝えない | live を伝える |
|---|---:|---:|
| \|roll\| / \|pitch\| | 1.5° / 1.7° | **0.1° / 0.0°** |
| \|yaw 誤差\| | 0.6° | **0.0°** |
| **水平ドリフト** | **1.36 m** | **0.02 m** |
| 深度ドリフト | −2.50 m | −0.89 m |

**効くのは主に並進**（姿勢は浮力の復元と過剰な制御でそれなりに保ててしまう）。
**yaw だけの偽機体では差が出なかった** — 3 基でも誤ったモデルのまま yaw を作れるため。
力の側を入れて初めて見える。

残る 0.89 m の浮上は縮退とは別件で、古典の heave が前進項だけ（`k_v_vert` 既定 0）で
深度を閉じていないため。**余裕は無くなる**ので cap を上げるか機動をゆっくりにすること。

- **2 基以上の欠損は受け付けない**（6 自由度の権限が無くなり、黙って姿勢が崩れるため）。
- **RL は使えない。** 方策は 4 基前提で学習しており、縮退の手段が無い。**古典を使うこと。**

### B-17. 【高・修正済み】現場向けの `ros2 param set` が黙って効かなかった — 「回転できない」の正体

2026-09-13 プール。**姿勢制御を効かせたままゲームパッドで操作すると、並進はできるが
回転がほとんどできない。** 推力の符号を疑って時間を使ったが、原因は符号ではなかった。

**原因 (1): `cmd_target_yaw_mode` の既定 `absolute` + 実行中に変えられない**

UI が出す `orientation.z` は**正規化したスティック値**（左スティック左右に ×−0.2）。
`absolute` ではこれを**絶対方位 [rad]** として読むので **±11° で頭打ち**になる。
手順書はこれを見越して `ros2 param set /classical_attitude cmd_target_yaw_mode rate` と
書いてあったが、**ノードは起動時に一度読むだけで、`_on_params` が受けていなかった。**

  → `ros2 param set` は **`successful=True` を返すのに挙動が変わらない**。
    現場からは「param set したのに回らない」としか見えず、切り分けが符号の方へ逸れる。

同じ状態だったものが 5 つ（すべて手順書が `param set` しろと書いているもの）:

| ノード | パラメータ | どこに書いてあったか |
|---|---|---|
| `/classical_attitude` | `cmd_target_yaw_mode` | field_card / teleop_gamepad / scenario_run |
| `/classical_attitude` | `cmd_target_yaw_rate_scale` | teleop_gamepad |
| `/classical_attitude` | `cmd_target_vel_scale` | teleop_gamepad |
| `/classical_attitude` | `live_thrusters_source` | field_card |
| `/navigator_node` | `yaw_rate_scale` | field_card / scenario_run（**コールバック自体が無かった**） |

**原因 (2): 旋回レートが UI の送信レートに依存していた**

`_on_cmd_target` は**指令を受けるたび**に呼ばれるのに、積分に制御周期
（`control_hz` 既定 50 Hz）を使っていた。UI の送信は 30 Hz（`gamepadPublisher.ts` の
`frequency = 30`）なので、**指定した rad/s の 0.6 倍でしか回らない。** UI 側の頻度を
変えると旋回速度が黙って変わる。

**対処**

- 上の 5 つを `_on_params` で受ける。値の検証つき（`cmd_target_yaw_mode` は
  `absolute` / `rate` 以外を拒否）。`live_thrusters_source` だけは**その場で読み直さない** —
  パラメータコールバックの中で control へ問い合わせると spin が入れ子になって固まるため、
  「次に `live_thrusters` を set するか再起動で効く」と警告を出すに留める。
- 旋回レートの積分を**受信間隔の実時間**にする（`advance_yaw_setpoint`）。途切れたときに
  目標が飛ばないよう `YAW_DT_MAX = 0.2 s` で頭打ち。
- `cmd_target_topic` を受けていて `absolute` のままなら、**起動時に警告を出す**
  （「±11° しか回れない」と直すコマンドを添えて）。
- 回帰テスト `umiusi_autonomy/test/test_cmd_target_yaw.py`。**手順書の
  `ros2 param set /<node> <param>` を全部拾って、そのノードのコールバックが
  受けているかを突き合わせる**テストを含む（修正前のコードに当てると上表の 5 つが出る）。

**検証**（ノードを立てて UI 相当の Target を実時間で 3 秒送る。左スティック −0.2）

| | 回った角度 | 目標方位 |
|---|---:|---:|
| `absolute`（既定・修正前と同じ） | 0° | **−11.5° で頭打ち** |
| `ros2 param set ... rate` 後 | **−52.1°** | 追随 |
| 同上・送信 10 Hz | **−50.5°**（レート非依存） | 追随 |

### B-19. 【高・修正済み】指令や IMU が途切れても最後の値のまま走り続けていた

姿勢制御器 (`classical_attitude`) は**スラスタを叩く唯一のノード**なのに、入力が
途切れたことを検出していなかった。どちらも**エラーを出さずに走り続ける**形。

**① 速度指令のデッドマンが無かった**

`/cmd/target`（UI テレオペ）も `~/setpoint`（FSM）も、最後に受けた値が
`self._vel_cmd` に残り続ける。テザー / Wi-Fi / rosbridge が切れても、**機体は最後の
スティック値のまま泳ぎ続ける。** 2026-09-13 の bag に
`manual_target_generator: Target is not updated` が **421 件**残っており、
実機で実際に起きている。`rl_attitude_node` には `vel_timeout` があった。

**② IMU の断を見ていなかった**

`ImuSanity` は 1 サンプルの化けを弾くだけで、**断は見ない**。IMU が止まると
`self._quat` が凍り、**姿勢誤差が一定のまま同じトルクを出し続けて機体が回り出す**
（誤差が縮まらないので出力も減らない）。起動直後に arm した場合も、姿勢の基準が
無いまま（単位クォータニオン＝水平とみなして）推力を出していた。

**対処**

| パラメータ | 既定 | 断のときどうするか |
|---|---|---|
| `vel_timeout` | **1.0 s** | **並進を 0 にする。姿勢目標は保持。** 出力ごと切ると正浮力で浮上するため |
| `imu_timeout` | **1.0 s** | **出力を 0 にする。disarm はしない。** 0 出力は浮上側に外れる（沈むより安全） |

- どちらも **0 以下で無効**にできる。実行中に `ros2 param set` で変えられる。
- **既定で有効にした。** `rl_attitude_node` の `vel_timeout` は既定 0（無効）だが、
  こちらはスラスタを叩く唯一のノードなので既定で入れる。**既定が 0 だと、
  いざというときに入っていない**（B-17 で学んだ形）。
- 指令 / IMU が戻れば**自動で復帰**する。復帰もログに出す。
- disarm でデッドマンは武装解除する。disarm 中に溜まった「来ていない時間」を持ち越すと、
  再 arm の初手で誤検出する。
- `tools/preflight.py` が「無効になっていないか」を出艇前に見る。

**保護の外にあるもの**（レビューで出た穴。**塞いでいないことを明記する**）

- **`vel_cmd` で入れた静的な巡航はデッドマンで守れない。** 生存を確認する相手が
  居ないため。武装させると `vel_timeout` 秒で勝手に 0 になり、`vel_cmd` 自体が壊れる。
  **起動時に「デッドマンの保護外」と警告を出す**ことで塞ぐ代わりとする。
  止めるのは disarm / e-stop だけ。
- **disarm は速度指令そのものを `vel_cmd` の値へ戻す。** 時計だけ戻して指令を残すと、
  「指令が途切れた → disarm → 再 arm」で**保護が外れたまま古い速度で走り出す**。
  時計と指令はセットで戻す。
- **失敗カウンタも disarm で戻す。** 持ち越すと再 arm 後の 1 回目の失敗で即 disarm になり、
  「1 サンプルの化けで run を終わらせない」という目的が消える。
- **例外時の 0 出力は disarm 中は publish しない。** `_emit` は `runnable=true` を付けるので、
  e-stop 中に出すと毎周期 attach し直すことになる。

**既知の穴**: 中継ノードが**古い値を publish し続ける**場合、メッセージは届くので
デッドマンは効かない。2026-09-13 の `Target is not updated` はまさにその状態だった
可能性がある（`/cmd/target` は 24 Hz 出続けていた）。**中継側で「更新が止まったら
publish も止める / 0 を出す」を入れないと塞ぎきれない。** core 側の
`manual_target_generator` の課題。

**追記 (2026-09-27): 回転中の符号反転は、静止からの起動よりずっと軽い**

sim 側が「esc の符号反転のたびに 2.7 s を払う」モデルで評価したところ姿勢誤差が 8 倍に
悪化したため、**その仮定が上界かどうか**を 9/13 の bag で測った。rpm は符号付きの実測なので

### B-21. 【高・設計判断で解消】指令 0 でも推力が出続けていたのは **浮力トリム**

| run (cap=`max_duty`) | 指令 0 の標本 | net 鉛直 (中央) | net 水平 (中央) | 1 基あたり &#124;duty&#124; (中央) | cap に対して |

1. **可動域が返ってくる。** 機動に使える推力が cap の半分以上、常時トリムに食われていた
2. **サーボの 180° 反転が減るはず。** `classical.py:242` に

3. 発熱・電流・電池の消費がそのぶん減る

**→ 対処は D-3 の決定どおり**（`autonomy_control_delta.md`）: **ソフトのトリムは持たず、
