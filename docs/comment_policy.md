# コメントの書き方

このリポジトリのコメント / docstring の基準。AI エージェントが書く分量が実装の 1/3 に達し、
かつ古い記述がそのまま残っていたため 2026-08-30 に定めた（PR #29）。

## 判定基準

> 消したら、テストが捕まえられない間違った変更を誰かがするか？

イエスなら残す。ノーなら消すか、既にある 1 箇所を指す。

## 残してよいのは 3 種類だけ

いずれも、このリポジトリのテストでは原理的に捕まらないもの。

1. **リポ / プロセスをまたぐ規約** — テストは各 repo の中で閉じている。
   例: 「値は sim の `configs/umiusi.yaml` と揃えること」
2. **呼び出し側の義務** — モジュールは自分の呼び出し側をテストできない。
   例: 「`max_duty` は方策が観測しているのと同じ値を渡す」
3. **実験 / ハードウェアのプロトコル** — ソフトの失敗モードが無い。
   例: 「`servo_sign` は実験 1 で確認してから変える」

## 消すもの

- **テストが既に assert している挙動** — テスト名を指すだけにする
- **経緯・実測値・過去の失敗** — `known_issues` / issue / README の ID を指すだけにする
- **コードを読めば分かる説明**

残す前に必ず `grep` すること。`docs/` や README に既にある内容を「テストで捕まらないから」
と残してしまう失敗が実際に起きている。

## 書き方

- 散文ではなく箇条書き。**規約**（単位・符号・不変条件）と**禁止事項**を分ける
- **レンダラが消費しない記法は書かない。** `**` 強調、`` ` `` / ` `` ` のコード引用、
  リンク、見出しは、それを描画するツールがこのリポジトリに実在するときだけ使う。
  現状 Python の docstring レンダラは無い（`conf.py` / `mkdocs.yml` / autodoc / `.rst` /
  doc CI ジョブ いずれも不在）ので、コード内では使わない。**この Markdown ファイルは
  レンダリングされるので対象外。**
- ただし**素のテキストとして読める構造は残す** — 箇条書き、字下げ、`規約:` のようなラベル。
  レンダラ無しでも機能するので装飾ではない
- **解決しない番号・略号を裸で置かない。** `REP-103` 単体は不可、`known_issues A-13` は可
- 参照は `grep` できる形にする。**節見出しを引くときは見出しと一字一句合わせる。**
  「上記参照」「詳しくは docs」は検証できないので禁止
- **実行時にユーザーへ出る文字列**（ロガー出力、launch の `description`、例外メッセージ）は
  この掃除の対象外。挙動として見えるテキストなので、変えるなら意図的に変える

## 比率について

**目標ではなく smell detector。** 200 行を超えるファイルにだけ当てる。22 行のモジュールの
うち 10 行が「sim と値を揃えろ」という禁止事項なら、45% でも正しい状態。

## docs 側も対象

コードから `docs/` へ移しても腐りは直らない。**移した先も同じ棚卸しの対象**にすること。
実際、`known_issues` B-12 は control の実装と矛盾したまま残っていた（PR #30 で訂正）。
同じ事実が複数箇所にあるのが本体の問題なので、**1 箇所 + 参照**にする。

## テストのコメント

テスト自身の設計理由（「mutation で確認した」「実装から定数を持ってくると検出できない」）は
テストでは表現できないので残す。ただし圧縮する。
